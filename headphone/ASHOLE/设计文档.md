# ICS43434 远距离对讲音频方案

## 1. 目标

实现基于 ICS43434 数字麦克风的远距离语音对讲，同时兼顾带宽、丢包、延迟和 ESP32 的处理能力。

不建议在公网或 Bluetooth PAN 链路中直接传输原始 PCM。16 kHz、16 bit、单声道 PCM 需要约 256 kbps，而且没有压缩和丢包恢复能力。推荐使用 Opus 压缩，并通过 UDP 传输。

## 2. 音频采集格式

ICS43434 的原始输出格式：

```text
接口：I2S
编码：线性 PCM
数据：有符号二进制补码
有效位宽：24 bit
顺序：MSB first
声道：由 L/R 引脚选择左声道或右声道
```

ESP32 的 I2S 外设通常按 32 bit 数据槽接收，因此应用层需要根据实际对齐方式取出有效的 24 bit 数据，再转换成 Opus 接受的 16 bit PCM。

推荐的语音输入格式：

```text
采样率：16 kHz
位宽：16 bit signed PCM
声道：单声道
字节序：小端序
帧长：20 ms
每帧采样点：320
每帧 PCM 大小：640 字节
```

24 bit 转 16 bit 的示意代码如下，实际移位量必须根据 I2S 驱动的数据对齐方式确认：

```c
int32_t sample_24 = sample_32 >> 8;
int16_t sample_16 = sample_24 >> 8;
```

语音对讲通常不需要保留 24 bit 精度。使用 16 bit PCM 可以降低带宽和内存占用，同时保留足够的语音动态范围。

## 3. 总体数据链路

```text
ICS43434
    -> I2S DMA
    -> 音频采集任务
    -> 环形缓冲区
    -> 24 bit 转 16 bit PCM
    -> Opus 编码
    -> UDP 音频包
    -> 公网服务器或中继
    -> UDP 音频包
    -> 接收端抖动缓冲
    -> Opus 解码
    -> I2S DAC/功放
```

PANU 只负责让 ESP32 通过 iPhone 获得网络连接，不能自动解决公网 NAT。两个设备在不同网络中进行对讲时，建议使用公网 UDP 中继服务器；服务器只转发已认证的音频包，不参与音频编解码。

## 4. Opus 参数

第一版实现建议使用以下参数：

```text
应用模式：OPUS_APPLICATION_VOIP
采样率：16 kHz
声道：Mono
帧长：20 ms
码率：16~24 kbps
编码复杂度：3~5
```

Opus 编码器通常接收 `int16_t` PCM。16 kHz、单声道、20 ms 的每帧输入为 320 个采样点。Opus 输出的是独立压缩数据包，不是 WAV 文件，也不需要在实时传输中套 Ogg 容器。

建议开启 Opus 的抗丢包能力：

```c
opus_encoder_ctl(enc, OPUS_SET_INBAND_FEC(1));
opus_encoder_ctl(enc, OPUS_SET_PACKET_LOSS_PERC(10));
opus_encoder_ctl(enc, OPUS_SET_DTX(1));
```

- `INBAND_FEC`：利用后续音频帧携带的信息恢复前一帧丢失的数据。
- `PACKET_LOSS_PERC`：告诉编码器预计丢包率，初始值可以设为 5~10，并根据实测情况调整。
- `DTX`：没有人说话时减少发送量；如果需要持续音频时钟，可以关闭该选项。

FEC 主要适合孤立丢包。连续丢包仍需要 PLC、扩大抖动缓冲区或降低码率，不能完全依靠重传解决。

## 5. UDP 封包

实时语音优先使用 UDP，避免 TCP 丢包重传造成队头阻塞和延迟突增。每个 UDP 音频包至少包含：

```text
协议版本       1 字节
标志位         1 字节
音频流 ID      2 字节
包序号         4 字节
采样时间戳     4 字节
Opus payload   变长
```

接收端通过包序号检测丢包，通过时间戳恢复播放节奏。Opus 负载很小，通常不会接近常见网络的 MTU；仍应将完整 UDP 包控制在约 1200 字节以内，避免 IP 分片。

## 6. 抖动缓冲与延迟

接收端不能收到一个包就立即播放，应先放入抖动缓冲区。建议初始配置为：

```text
目标缓冲：60~80 ms
网络波动较大时：最高扩展到 120 ms
```

缓冲越大，抗抖动能力越强，但对讲延迟也越高。对讲业务应优先控制端到端延迟；如果连续丢包，使用 Opus PLC/FEC 补帧，避免等待过期重传数据。

## 7. 带宽对比

| 音频格式 | 原始码率 |
| --- | ---: |
| 8 kHz / 16 bit / Mono PCM | 128 kbps |
| 16 kHz / 16 bit / Mono PCM | 256 kbps |
| 16 kHz / 24 bit / Mono PCM | 384 kbps |
| 16 kHz / Mono Opus | 16~24 kbps |

上述数值未计入 UDP、IP、链路层和自定义包头开销。对于 Bluetooth PANU 链路，直接传 16 kHz PCM 需要实测吞吐和稳定性；Opus 能留下更大的带宽余量。

## 8. ESP32 移植风险与规避措施

1. **CPU 占用**：使用固定点 Opus，先采用 16 kHz、Mono、20 ms 和复杂度 3~5；不要在 I2S 中断中执行编码。
2. **RAM/Flash 占用**：只编译需要的编码器功能，尽量关闭不使用的解码器；编码器状态、DMA 缓冲区和环形缓冲区优先静态分配，避免实时任务频繁申请释放堆内存。
3. **实时性**：采用 `I2S DMA -> 采集任务 -> 环形缓冲区 -> Opus 编码任务 -> 发送任务`，并监控编码耗时和缓冲区水位。
4. **采样率漂移**：发送端和接收端时钟存在误差，长时间运行需要监控抖动缓冲水位，并通过丢/补一个采样点或轻微重采样控制水位。
5. **链路共存**：PAN、网络栈和音频任务会竞争 CPU；需要测试 Bluetooth PAN、Opus 和发送任务同时运行时是否出现 I2S DMA 溢出。
6. **安全性**：公网传输不能发送明文语音，后续应加入设备鉴权和 DTLS/SRTP 或基于 mbedTLS 的认证加密。

## 9. 实施顺序

1. 在局域网中完成 ICS43434 I2S 采集和 16 bit PCM 播放，确认数据对齐、音量和噪声正常。
2. 在单机上加入 Opus 编码和解码，验证编码耗时、内存余量和语音质量。
3. 实现 UDP 音频包、序号、时间戳和接收端抖动缓冲。
4. 加入 PLC、FEC、动态码率和断线重连处理。
5. 将 UDP 端点改为公网中继服务器，并加入鉴权和加密。
6. 在 Bluetooth PAN、弱信号、连续丢包和长时间运行条件下进行压力测试。

## 10. 验收指标建议

```text
端到端延迟：目标小于 200 ms
正常网络丢包：语音连续，无明显卡顿
5% 随机丢包：可以通过 FEC/PLC 保持可懂度
编码任务：不能导致 I2S DMA 溢出
长时间运行：抖动缓冲水位不持续增长或下降
公网环境：断线后可以自动重连，未经认证的包被丢弃
```
